## 6. 多节点多线程并发（绕过单Executor瓶颈）

**工作线程数**: 4　（每个线程独立创建 Node + Executor）

### 6.1 多节点 Topic 发布

| 指标 | C++ | Python | Rust |
|------|-----|--------|------|
| total_sent | 4,000 | 4,000 | 4,000 |
| total_received | 2,048 | 2,004 | 4,000 |
| elapsed_s | 0.31 | 0.55 | 0.11 |
| aggregate_throughput | 6701.20 | 3640.39 | 36977.33 |
| avg_latency_us | 9816.66 | 75940.50 | 34667.30 |

### 6.2 多节点 Service 调用

| 指标 | C++ | Python | Rust |
|------|-----|--------|------|
| total_calls | 400 | 400 | 400 |
| elapsed_s | 0.01 | 5.17 | 0.04 |
| aggregate_throughput | 40266.30 | 77.32 | 11200.76 |
| avg_latency_us | 96.49 | 14250.33 | 151.95 |

> **总结**: 多节点Topic发布 Rust吞吐最高；多节点Service调用 C++吞吐最高。
> **关键对比**: Rust多节点模式Service吞吐量是单Executor并发模式的 **2155倍** (11201 vs 5.2 ops/s)，充分证明了多节点多线程模式绕过BasicExecutor瓶颈的巨大效果。
> Rust多节点Topic仅接收 100% 的消息，这并非多节点模式的缺陷，而是独立Context之间DDS发现延迟(1-2s)导致的。Topic发布本身是线程安全的无锁操作，多节点模式的核心价值体现在需要Executor回调处理的Service场景。
> 多节点多线程模式下，每个线程拥有独立的Executor和Node，消除了共享Executor的串行瓶颈。C++利用MultiThreadedExecutor本身已能高效并行；Rust通过多节点模式弥补了BasicExecutor的单线程限制，Service性能提升数个数量级；Python虽有独立Node但GIL仍限制并行度。此模式是当前rclrs实现高并发ROS2通信的最佳实践。

## 8. 安全性评估

| 维度 | C++ | Python | Rust |
|------|-----|--------|------|
| 内存安全 | 手动管理，有UAF/溢出风险 | GC自动管理，安全 | 所有权系统，编译期保证 |
| 线程安全 | 需手动加锁，有数据竞争风险 | GIL限制真并行 | Send/Sync trait编译期保证 |
| 空指针 | 可能出现 | 无(None代替) | Option<T>编译期强制处理 |
| 未定义行为 | 可能出现 | 不会 | 仅unsafe块中可能 |
| 类型安全 | 弱(隐式转换) | 动态类型 | 强类型+泛型 |

> **总结**: Rust在所有安全维度上表现最优——所有权系统、Send/Sync trait、Option<T>和强类型系统在编译期即消除了内存泄漏、数据竞争、空指针和类型错误。C++灵活但需开发者自行保证安全，高并发场景下数据竞争风险显著增加。Python通过GC和GIL在单线程场景安全性好，但GIL限制了真并发能力，且动态类型在大型项目中增加运行时错误风险。
